# FastAPI database migrations with Alembic

This skill changes a FastAPI app's PostgreSQL schema only through Alembic revisions that are reviewed, reversible and
never edited after they ship. Checked with Alembic 1.20.1 and SQLAlchemy 2.1.6.

## Step 0: installed versions for migrations

Read the versions and the state of the database first. A missing line means the package is not installed.

```bash
uv pip list | grep -iE '^(alembic|sqlalchemy|asyncpg|psycopg) '
uv run alembic current
uv run alembic heads
```

The `pyproject_async` template needs an Alembic release that has `[tool.alembic]` support (1.16 or later), and
`uv run alembic list_templates` shows whether yours does.

## Set up Alembic with the async template

Alembic ships templates for async drivers; `pyproject_async` keeps the configuration in `pyproject.toml` under
`[tool.alembic]`. It leaves logging in `alembic.ini` and a placeholder `sqlalchemy.url` line there: delete that line,
because `env.py` below takes the URL from the settings.

```bash
uv add alembic
uv run alembic init -t pyproject_async migrations      # or -t async for a classic alembic.ini
uv run alembic list_templates                          # generic, async, pyproject, pyproject_async, multidb
```

Then edit `migrations/env.py` so it reads the URL from the app settings and compares against the app's metadata.

```python
# migrations/env.py
import asyncio

from alembic import context
from sqlalchemy import pool
from sqlalchemy.engine import Connection
from sqlalchemy.ext.asyncio import create_async_engine

from app.config import get_settings
from app.models import Base          # import the module that imports every model

config = context.config
target_metadata = Base.metadata


def database_url() -> str:
    return config.attributes.get("database_url") or str(get_settings().database_url)


def run_migrations_offline() -> None:
    context.configure(url=database_url(), target_metadata=target_metadata, literal_binds=True,
                      dialect_opts={"paramstyle": "named"}, compare_type=True)
    with context.begin_transaction():
        context.run_migrations()


def do_run_migrations(connection: Connection) -> None:
    context.configure(connection=connection, target_metadata=target_metadata, compare_type=True)
    with context.begin_transaction():
        context.run_migrations()


async def run_async_migrations() -> None:
    engine = create_async_engine(database_url(), poolclass=pool.NullPool)
    async with engine.connect() as connection:
        await connection.run_sync(do_run_migrations)
    await engine.dispose()


if context.is_offline_mode():
    run_migrations_offline()
else:
    asyncio.run(run_async_migrations())
```

- `config.attributes["database_url"]` lets tests pass a container URL without touching environment variables.
- Leave `sqlalchemy.url` out of the config files; the URL holds a password.
- Set the metadata naming convention before the first revision (fastapi-sqlalchemy-async), or constraint names
  differ between environments and later drops fail.

## The change workflow

Every schema change follows the same five steps, in order.

```bash
# 1. change the models in app/<domain>/models.py
# 2. generate a revision against an up-to-date database
uv run alembic upgrade head
uv run alembic revision --autogenerate -m "add items.archived_at"
# 3. read and fix the generated file (see the review list below)
# 4. apply it, roll it back, apply it again
uv run alembic upgrade head && uv run alembic downgrade -1 && uv run alembic upgrade head
# 5. prove models and migrations agree
uv run alembic check
```

Useful commands: `alembic current` (revision of the database), `alembic history --verbose`, `alembic heads`,
`alembic upgrade head --sql` (print SQL without running it, for a DBA review).

## Review every autogenerated revision

Autogenerate compares models with the database and guesses; it is a draft, not a migration. Check each file for:

- **Renames** show up as drop plus add, which loses data. Replace them with `op.alter_column(..., new_column_name=...)`
  or `op.rename_table()`.
- **Not detected at all:** changes to server defaults on some types, `CHECK` constraint bodies, enum value changes,
  sequences, views, triggers and functions. Write those by hand.
- **Type changes** are detected by default (`compare_type` defaults to `True`; `env.py` above states it anyway) and
  often need a `postgresql_using="col::integer"` clause.
- **A new non-nullable column** on a table with rows fails; add it nullable, backfill, then set `nullable=False`, or
  give it a `server_default`.
- **`downgrade()`** must undo `upgrade()` exactly. If a step cannot be undone (data deleted), raise
  `NotImplementedError` with a reason instead of leaving `pass`.
- **Empty revision** after autogenerate means models and database already agree; delete the file.

More traps (enums, SQLModel's `AutoString`, server defaults, multiple metadata): [references/autogenerate.md](references/autogenerate.md).

## Migrations are immutable once shared

A revision that has been merged or applied to any shared database is history. Editing it makes databases that already
ran it differ from new ones, silently.

- Fix a bad migration with a new revision that corrects it.
- Only an unmerged revision on your own branch may be edited, and then re-applied with `downgrade -1` and `upgrade head`.
- `scripts/check_migrations.sh` fails a branch that modifies, renames or deletes an existing revision file.

## Data migrations

A data migration changes rows, not structure. Write it with Core statements against a lightweight table definition,
never with the app's ORM models, which will change later while the migration must not.

```python
import sqlalchemy as sa
from alembic import op

items = sa.table("items", sa.column("id", sa.Integer), sa.column("status", sa.String))


def upgrade() -> None:
    op.add_column("items", sa.Column("status", sa.String(20), nullable=True))
    op.execute(items.update().where(items.c.status.is_(None)).values(status="draft"))
    op.alter_column("items", "status", nullable=False)


def downgrade() -> None:
    op.drop_column("items", "status")
```

For millions of rows, backfill in batches in a separate script or job so the migration does not hold a long lock.

## Zero-downtime schema changes

During a rolling deploy old and new code run against the same schema, so every change must work with both. Split
breaking changes into expand, migrate, contract steps across releases.

| Change | Safe sequence |
|---|---|
| add a column | add it nullable (or with a server default) → deploy code that writes it → backfill → set NOT NULL |
| rename a column | add the new column → write both → backfill → read the new one → drop the old one in a later release |
| drop a column | stop reading and writing it in code → deploy → drop it in the next release |
| add an index on a big table | `CREATE INDEX CONCURRENTLY` outside a transaction (below) |
| add a foreign key | add it `NOT VALID`, then `VALIDATE CONSTRAINT` in a second step |

Set a lock timeout so a migration waiting for a busy table fails fast instead of blocking every query behind it:
`op.execute("SET lock_timeout = '5s'")` at the start of `upgrade()`.

## CREATE INDEX CONCURRENTLY

PostgreSQL builds a concurrent index without blocking writes, but not inside a transaction. Alembic runs each
revision in a transaction, so step out of it with `autocommit_block()`.

```python
def upgrade() -> None:
    with op.get_context().autocommit_block():
        op.create_index(
            "ix_items_title", "items", ["title"], postgresql_concurrently=True, if_not_exists=True
        )


def downgrade() -> None:
    with op.get_context().autocommit_block():
        op.drop_index("ix_items_title", table_name="items", postgresql_concurrently=True, if_exists=True)
```

A failed concurrent build leaves an `INVALID` index behind; `if_not_exists=True` would then skip it. Check
`SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;` and drop it before retrying.

## Branches and merge heads

Two branches that each add a revision on the same parent give Alembic two heads, and `upgrade head` refuses to run.
Merge them with an empty revision after both are merged.

```bash
uv run alembic heads
uv run alembic merge heads -m "merge items and users heads"
```

## Running migrations at deploy

Run migrations once per deploy, before the new app version takes traffic, from one process; never from the app's
lifespan, where every worker would race to apply them.

- A pre-start step: `uv run alembic upgrade head && exec fastapi run` in the container entry script, only if there is
  one replica; otherwise
- a separate job (a Kubernetes `Job` or init container, a CI deploy step) that runs `alembic upgrade head` and must
  succeed before rollout.
- The database role used for migrations owns the tables; the app's runtime role needs only `SELECT`, `INSERT`,
  `UPDATE`, `DELETE`.

## Migrations in tests and CI

Tests build their schema by running the migrations, not `Base.metadata.create_all()`, so a broken migration fails CI
instead of production. From an async pytest fixture, run Alembic in a worker thread because `env.py` calls
`asyncio.run()`:

```python
from alembic import command
from alembic.config import Config

cfg = Config(toml_file="pyproject.toml")          # pyproject_async template; use Config("alembic.ini") otherwise
cfg.attributes["database_url"] = database_url
await asyncio.to_thread(command.upgrade, cfg, "head")
```

In CI run `scripts/check_migrations.sh origin/main` against a scratch database: no edited revisions, one head, a full
upgrade, downgrade, upgrade round trip, and `alembic check`.

When a script from `scripts/` is not on disk (a pack install), read that script from the library that served this page and save it first.

## Verify a migration before merging

Run the script against a scratch database, never a shared one, since step 3 downgrades to base and drops every table.

```bash
scripts/check_migrations.sh --help                 # usage, exit 0
scripts/check_migrations.sh origin/main            # no edited revisions, one head, round trip, alembic check
uv run alembic upgrade head --sql | less           # the SQL a DBA would review
```

On a large table, also read the plan for locks: run the migration on a copy of production-sized data, and check that
`lock_timeout` is set in every revision that takes one.

## Migration anti-patterns

Each of these has taken a production database down or lost data.

| Do not | Do instead |
|---|---|
| edit a merged revision | write a new revision that corrects it |
| run `alembic upgrade head` in the lifespan | one release step, before the new code takes traffic |
| import app models in a data migration | a `sa.table()` definition |
| accept a drop plus an add for a rename | `op.alter_column(..., new_column_name=...)` |
| add a NOT NULL column to a full table in one step | add it nullable, backfill, then set NOT NULL |
| `CREATE INDEX` on a big table inside the transaction | `postgresql_concurrently=True` in `autocommit_block()` |
| leave `pass` in `downgrade()` | undo the change, or raise `NotImplementedError` with a reason |

## Alembic migration checklist

Go through this Alembic migration checklist before merging a change.

```text
[ ] env.py reads the URL from settings and uses the app's Base.metadata
[ ] naming convention set on the metadata before the first revision
[ ] every autogenerated file reviewed: renames, defaults, enums, NOT NULL on existing tables
[ ] downgrade() reverses upgrade() or raises NotImplementedError with a reason
[ ] no shared revision edited; fixes are new revisions
[ ] data migrations use sa.table() definitions, never app models; large backfills batched
[ ] breaking changes split into expand and contract releases; lock_timeout set
[ ] big-table indexes built CONCURRENTLY in autocommit_block
[ ] one head; migrations run once per deploy, outside the app process
[ ] tests and CI build the schema through migrations; alembic check passes
```

## Common Alembic migration problems

These are the Alembic migration problems people hit most, each with its symptom, cause and fix.

1. **Autogenerate wants to drop every table.** `env.py` imports `Base` but not the modules that define the models.
   Import every model module where `Base.metadata` is built.
2. **`asyncio.run() cannot be called from a running event loop`.** Alembic was called directly inside an async test
   or the app. Run it in a thread (`asyncio.to_thread`) or from the command line.
3. **`Target database is not up to date`.** Autogenerate needs the database at `head` first: `alembic upgrade head`,
   then `revision --autogenerate`.
4. **`CREATE INDEX CONCURRENTLY cannot run inside a transaction block`.** Wrap it in `autocommit_block()`.
5. **Enum changes ignored.** Autogenerate does not alter PostgreSQL enum types; add values with
   `op.execute("ALTER TYPE item_status ADD VALUE 'archived'")`, or use a `String` column with a `CHECK` instead of a
   native enum.
6. **`alembic check` passes but production differs.** Someone changed production by hand. Compare with
   `alembic upgrade head --sql` and a schema dump; never "fix" by editing old revisions.
